# Model card: Aegis fraud MLP v1

Banks are expected to document models like this under model-risk guidance such as the US Federal Reserve's
SR 11-7. This card follows the "Model Cards for Model Reporting" format (Mitchell et al., 2019).

## Overview

| | |
|---|---|
| Task | Binary classification: is this payment fraudulent? |
| Architecture | MLP 20 → 32 → 16 → 1, ReLU, sigmoid output |
| Training | NumPy from scratch, weighted binary cross-entropy, Adam, early stopping on validation PR-AUC |
| Serving | C++ (`aegis::Mlp`), ~140 ns per inference, combined with 6 deterministic rules |
| Artifact | `models/aegis.model` (SHA-256 checksum) + `.sig` (HMAC-SHA256) |
| Fingerprint | Recorded in `reports/metrics.json` and in every audit record |

## Intended use

- **Intended:** to rank and triage card and transfer payments for human review, and to block when the score is
  very high. It is decision *support* in a pipeline where analysts make final calls on reviewed cases.
- **Not intended:** credit decisions, customer profiling, or any use on real customers without retraining and
  validation on real data.

## Data

Synthetic, generated by `aegis.datagen` (seed 7): 5,000 accounts over 60 days, 615,387 transactions, 0.99% fraud.

| Fraud typology | What the simulator injects |
|---|---|
| account_takeover | New device, often a new country, 5–40× normal spend, high-risk categories |
| card_testing | 4–12 sub-$5 charges at new merchants within minutes, sometimes followed by a cash-out |
| cloned_card | Card-present use in a distant country 10–90 minutes after a genuine purchase |
| structuring | 3–6 transfers of $9,000–$9,990 a few hours apart |
| bust_out | 10–25 rapid purchases at 1.5–8× normal spend |

Hard negatives (legitimate behaviour that resembles fraud) are deliberate: trips abroad with realistic flight
gaps, new phones, occasional 5–15× purchases, and rare legitimate ~$9.5k transfers.

**Split:** by time, 70% train / 15% validation / 15% test. Features are point-in-time, so no feature uses
information from after the transaction.

## Features

Twenty behavioural features: amount and its z-score against the account's history, decayed transaction counts
(10 min / 1 h / 24 h), spend velocity, distance and implied speed from the previous transaction, novelty of
device, merchant and country, time of day (cyclical), merchant-category risk, channel, round and near-threshold
amounts, and history length. Definitions are in `core/include/aegis/types.hpp`.

**No protected attributes** (age, gender, ethnicity, nationality) are used. Country is used as a *change*
signal ("new for this account"), not as a risk level per country. That still needs a fairness review on real
data, because location can be a proxy for protected characteristics.

## Performance (test split, never seen in training or threshold selection)

| Metric | Value |
|---|---|
| ROC-AUC | 0.999 |
| PR-AUC | 0.980 |
| Recall at 0.1% / 0.5% / 1% FPR | 95.9% / 98.0% / 98.5% |
| Deployed REVIEW-or-BLOCK: precision / recall | 65.8% / 97.8% |
| Deployed BLOCK: precision / recall | 93.6% / 92.4% |

Recall by typology at the deployed operating point: account takeover 100%, card testing 100%, structuring 100%,
bust-out 95.1%, cloned card 91.9%.

**Why these numbers are higher than real-world systems.** Synthetic fraud follows the patterns it was generated
from. Real fraud adapts, labels arrive late and are noisy (chargebacks take weeks), and legitimate behaviour is
far more varied. Treat these results as a check that the pipeline works, not as a performance claim.

## Thresholds

Thresholds are chosen on validation data by false-positive budget: REVIEW at a 0.5% FPR budget, BLOCK at 0.05%.
They are stored inside the signed model file so a model and its operating point cannot drift apart.

## Explainability

Every REVIEW/BLOCK decision carries reason codes computed by gradient × input in the C++ engine. For a linear
model this decomposition is exact; for the MLP it is a first-order (local) approximation and can over-weight
features with extreme values. Rule hits are exact and come with plain-English descriptions.

## Monitoring that a production deployment would need

- Score distribution and flag-rate drift (Population Stability Index per feature).
- Delayed-label performance once chargebacks arrive (precision/recall by typology, per week).
- Analyst override rate on REVIEW cases, which is an early warning that the model and reality disagree.
- Threshold re-calibration on a schedule, with sign-off recorded in the audit chain.

## Ethical considerations

- False positives have costs: blocked legitimate payments hurt customers, especially those travelling or with
  irregular incomes. That is why only very high-confidence scores BLOCK, while REVIEW routes to humans.
- The LLM investigator is advisory. It cannot dismiss hard-rule or BLOCKed alerts, and its reports are hashed
  into the audit trail.
